# 行存储与页组织

## 模块目标

这一层决定数据在磁盘和内存里如何组织。对接近生产可用的 MySQL 内核来说，它影响：

- 读写放大
- buffer pool 命中率
- 页分裂与空间回收
- 恢复和校验成本

## 当前仓库参照实现

主要参考：

- `storage/innobase/`: 页、段、extent、buffer pool、记录格式
- `storage/myisam/`: 另一种表/索引文件组织方式
- `storage/rocksdb/`: 作为不同存储模型的对照

如果以单机事务内核为主，最值得参考的是 InnoDB 风格的页式行存储。

## 如果你自己实现，应该怎么抽象

建议采用页式组织：

- 表空间由多个 page 组成
- page 上存放 record、slot、page header
- B+Tree 叶子页存放主记录或索引记录
- buffer pool 负责页缓存与脏页管理

第一版尽量避免过于复杂的分段空间管理算法，但页、空闲空间和页校验一定要从一开始设计清楚。

## 核心数据结构

- `PageId`
- `PageHeader`
- `RecordHeader`
- `SlotDirectory`
- `BufferFrame`
- `Tablespace`

## 关键流程

1. 根据 `PageId` 从 buffer pool 获取页
2. 若缺页则从磁盘读取
3. 在页内定位记录或空闲空间
4. 修改页并标脏
5. 后台线程刷脏和 checkpoint

## 工程实现建议

- 页大小、记录头和 slot 目录必须稳定，否则恢复、兼容和 online 校验都很困难。
- 第一版优先做“可恢复、可校验、可调试”的页格式，而不是最极致的压缩率。
- 页面校验和 LSN 必须内嵌在页头里，后面恢复会依赖它们。

## 最小可用版本

- 固定页大小
- 行记录页格式
- 空闲空间管理
- buffer pool 基础替换和脏页管理

## 继续演进方向

- 页压缩
- 更复杂的空间回收
- 热点页竞争优化
- 大字段外部存储与溢出页
