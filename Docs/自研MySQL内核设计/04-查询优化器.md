# 查询优化器

## 模块目标

优化器负责把已完成语义绑定的 SQL 语句转成代价更低的执行计划。单机接近生产可用的 MySQL 内核里，优化器不是“锦上添花”的模块，而是把 SQL 语义变成可承载业务负载的执行策略的地方。

它至少需要解决：

- 表访问路径选择
- 索引选择
- Join 顺序
- 排序、聚合、临时表和物化策略
- 统计信息驱动的粗粒度代价估计
- 输出可解释、可调试的物理计划

## 当前仓库参照实现

关键参考：

- `sql/sql_optimizer.cc`: `JOIN::optimize()`
- `sql/sql_select.cc`: 计划构建和部分选择逻辑
- `sql/opt_range.cc`: 范围访问优化
- `sql/records.cc`, `sql/filesort.cc`: 扫描与排序相关逻辑
- `sql/item*.cc`: 表达式选择性与执行代价输入

从当前仓库可以读出两个重要事实：

- MySQL 优化器不是单一函数，而是一串阶段化决策
- 访问路径、Join 枚举、排序/临时表策略和执行器能力是强耦合的

## 如果你自己实现，应该怎么抽象

建议采用“分阶段优化器”，而不是试图第一版就做一个巨大的统一 CBO。

推荐拆成五层：

1. `RewritePhase`
做常量折叠、布尔表达式归一化、谓词下推前准备。

2. `AccessPathPhase`
针对每张表枚举：

- 全表扫描
- 主键点查
- 主键范围查
- 二级索引查找
- 覆盖索引扫描

3. `JoinOrderPhase`
在候选访问路径的基础上枚举 Join 顺序。

4. `PhysicalPropertyPhase`
决定排序是否保留索引序、是否使用临时表、是否先 materialize。

5. `PlanFinalizePhase`
输出执行器能消费的物理计划树，并附带 `EXPLAIN` 所需元信息。

这种分法的好处是：每个阶段都能单独调试，也更适合逐步增强。

## 核心数据结构

- `Statistics`
  - `row_count`
  - `index_cardinality`
  - `distinct_count`
  - `null_fraction`
  - `hot_value_summary`

- `Predicate`
  表达过滤条件的标准化对象，供重写和选择率估计使用。

- `AccessPath`
  - `table_id`
  - `access_type`
  - `index_id`
  - `range`
  - `estimated_rows`
  - `cost`
  - `order_property`

- `JoinOrder`
  表示表连接顺序和各阶段估计代价。

- `Cost`
  建议拆成子项：
  - `cpu_cost`
  - `io_cost`
  - `memory_cost`
  - `sort_cost`
  - `materialize_cost`

- `LogicalPlan`
  语义层计划，用来承载 SQL 结构。

- `PhysicalPlan`
  执行器最终使用的计划树。

## 核心不变量

1. 优化器不改变 SQL 语义，只改变执行策略。
2. 任何代价估计都必须可追溯到统计信息和规则假设。
3. 访问路径比较必须使用统一代价单位，避免不同阶段口径不一致。
4. 优化器输出必须能映射到可解释的 `EXPLAIN` 结果。

## 统计信息设计

第一版优化器成败不在于枚举多复杂，而在于统计信息是否足够支撑决策。

建议至少有：

- 表总行数
- 聚簇索引页数
- 二级索引页数
- 索引前缀基数
- 主键/常见热点值近似分布

如果没有这些，优化器只能在“全表扫”和“索引扫”之间盲猜。

第一版不必做复杂直方图，但要设计可扩展接口：

- `estimate_selectivity(predicate)`
- `estimate_range_rows(index, range)`
- `estimate_distinct(index_prefix)`

## 访问路径枚举

### 单表访问类型

建议第一版支持以下访问路径：

- `FullTableScan`
- `PrimaryKeyLookup`
- `PrimaryKeyRangeScan`
- `SecondaryIndexLookup`
- `SecondaryIndexRangeScan`
- `CoveringIndexScan`

### 路径评价维度

每条访问路径应至少考虑：

- 预估返回行数
- 访问页数
- 是否需要回表
- 是否天然有序
- 是否能覆盖查询字段

特别要强调：

二级索引不是“只要命中条件就一定更好”，回表成本、随机 I/O 和结果集大小必须一起评估。

## Join 顺序设计

对于第一版，建议采用左深树（left-deep tree）枚举。

原因：

- 与 iterator 执行器天然匹配
- 更容易控制复杂度
- 对典型 OLTP 查询已足够实用

Join 枚举流程可以设计成：

1. 为每张表生成候选访问路径
2. 选定一张表作为驱动表
3. 逐步加入下一张表，累计代价
4. 保留 top-N 候选计划，做简单剪枝

第一版不建议一开始就做 bushy tree。

## 谓词处理与下推

建议把谓词分成三类：

- 可在访问路径阶段利用的索引谓词
- 可在连接阶段利用的 join 谓词
- 只能在执行器过滤阶段使用的残余谓词

优化器需要把它们提前标好，否则执行器会不得不重新分析一遍。

## 排序、聚合与临时表策略

优化器必须明确决定：

- 是否可直接利用索引顺序避免排序
- 是否需要 filesort
- 聚合是否可流式完成
- 是否必须 materialize 中间结果

建议把以下代价显式纳入模型：

- 排序输入行数
- 排序键宽度
- 临时表列宽和行数
- 内存是否足够，否则可能 spill

如果这些不显式建模，计划质量会在 `GROUP BY` / `ORDER BY` / 派生表场景迅速劣化。

## 子查询与物化策略

第一版可以保守，但必须先决定语义：

- 子查询是转 join，还是先 materialize
- 派生表何时物化
- `IN (subquery)` 是否简化为半连接

推荐第一版策略：

- 简单非相关子查询：优先 materialize
- 明确可 rewrite 的子查询：再做有限规则改写

不要一开始追求复杂半连接优化。

## 代价模型建议

第一版代价模型可以是简化版，但必须结构化。建议：

```text
total_cost =
  scan_cost +
  lookup_cost +
  cpu_eval_cost +
  sort_cost +
  materialize_cost
```

其中：

- `scan_cost`: 顺序页访问成本
- `lookup_cost`: 索引定位与回表成本
- `cpu_eval_cost`: 表达式和谓词求值成本
- `sort_cost`: 排序或重排成本
- `materialize_cost`: 写临时表和再读成本

第一版不要纠结“绝对精确”，但必须保证“相对可比”。

## EXPLAIN 与可解释性

优化器输出如果不可解释，后续调优基本无法推进。

建议第一版就输出：

- 访问类型
- 使用索引
- 估计行数
- 是否回表
- 是否排序
- 是否使用临时表
- Join 顺序

这部分不要等到后面再补。数据库项目里，缺少 `EXPLAIN` 往往会直接拖垮定位效率。

## 工程实现建议

- 第一版不要追求复杂 CBO。先把统计信息、访问路径和 Join 顺序三件事做稳。
- 访问路径、Join 枚举和排序决策最好拆成独立阶段，避免巨型函数。
- 统计信息接口一定要和存储引擎抽象层对齐，不能让优化器直接碰页结构。
- 优化器必须输出稳定计划对象，而不是把决定逻辑藏在执行器里。
- 临时表、排序和回表的代价要显式建模，不然计划质量会迅速失控。

## 第一版应该做什么，不该做什么

### 应该做

- 单表扫描和索引访问选择
- 两表到多表左深 Join 顺序选择
- 排序与聚合的显式代价考虑
- 简单子查询物化
- 基础 `EXPLAIN`

### 不该做

- 一开始就做全量 bushy tree 搜索
- 一开始就做复杂半连接优化
- 一开始就做依赖大量高级统计信息的代价模型

## 最小可用版本

- 单表访问路径选择
- 左深 Join 枚举
- 排序/临时表决策
- 简化代价模型
- `EXPLAIN`

## 继续演进方向

- 直方图与更强统计信息
- 更复杂的子查询优化
- 半连接、索引合并
- Plan cache 与 plan stability 策略
- 更细粒度代价反馈与自适应优化
