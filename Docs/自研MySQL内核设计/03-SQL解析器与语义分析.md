# SQL 解析器与语义分析

## 模块目标

该模块负责把 SQL 文本转成可执行的内部表示，并在执行前完成最基本的语义绑定。它要保证：

- 语法正确性
- 名称解析正确性
- 列、表、函数和系统变量引用合法
- 表达式具备明确的类型和语义

## 当前仓库参照实现

关键参考：

- `sql/sql_parse.cc`: SQL 命令分发、解析入口、执行入口
- `sql/sql_yacc.yy` 和生成的 `sql_yacc.cc`: 语法规则
- `sql/sql_lex.cc`, `sql/sql_lex.h`: 词法和语句对象
- `sql/item*.cc`: 表达式、函数、聚合等节点
- `sql/sql_resolver.cc`: 语义解析与名称绑定

## 如果你自己实现，应该怎么抽象

建议分三层：

1. 词法与语法层
输出原始 AST，只负责结构化，不做复杂语义判断。

2. 绑定层
把 AST 中的表名、列名、函数名、变量名解析到真实对象。

3. 规范化层
做类型推导、常量折叠、表达式重写，为优化器提供统一输入。

第一版不要试图把解析、绑定和优化全揉在一起，否则后期很难维护。

## 核心数据结构

- `Token`
- `ParserState`
- `ASTNode`
- `Statement`
- `Expr`
- `NameResolutionContext`
- `ResolvedTableRef`
- `ResolvedColumnRef`

## 关键流程

1. 将 SQL 文本切分成 token
2. 根据语法规则生成 AST
3. 创建语句级上下文
4. 解析表、列、别名、函数和系统变量
5. 对表达式做类型检查和必要重写
6. 输出可交给优化器的 `ResolvedStmt`

## 工程实现建议

- AST 和执行期表达式对象不要完全共用一套类型；执行器需要的是更稳定、更易求值的结构。
- 第一版就把名称解析上下文设计清楚，尤其是子查询、别名、派生表和多层作用域。
- 表达式类型系统必须可扩展，否则日期、字符串、NULL 语义会迅速失控。

## 最小可用版本

- `SELECT`, `INSERT`, `UPDATE`, `DELETE`
- `CREATE TABLE`, `DROP TABLE`, `ALTER TABLE` 的受限子集
- `BEGIN`, `COMMIT`, `ROLLBACK`
- 基础函数、比较、逻辑表达式、聚合

## 继续演进方向

- 更复杂的子查询与相关子查询
- 窗口函数
- 更完整的 JSON / GIS / 时间类型函数
- 更强的语句重写与规范化能力
