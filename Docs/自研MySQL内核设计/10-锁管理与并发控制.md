# 锁管理与并发控制

## 模块目标

该模块负责在多线程会话并发下保证正确性，并控制争用成本。接近生产可用的 MySQL 内核，不能只说“有锁”，而必须明确：

- 哪些是事务语义上的锁
- 哪些是保护内存结构完整性的短期同步原语
- DDL 与 DML 如何隔离
- 死锁如何检测和处理
- 高争用场景如何避免系统性退化

## 当前仓库参照实现

关键参考：

- `sql/mdl.cc`: 元数据锁
- `sql/lock.cc`: SQL 层锁相关逻辑
- `sql/sql_base.cc`, `sql/sql_table.cc`: 打开表与 DDL 路径上的锁协调
- `storage/innobase/lock/`: 行锁与事务锁
- `storage/innobase/sync/`: latch / mutex / rwlock 等同步原语

当前仓库给出的最重要经验不是“锁种类很多”，而是锁被清晰分成了不同层次，每层有不同职责。

## 如果你自己实现，应该怎么抽象

必须从一开始明确区分三类并发对象：

1. `Latch`
保护内存结构完整性，持有时间短，通常不跨 I/O，不参与事务语义。

2. `TxnLock`
保护事务语义，如行锁、间隙锁、意向锁，可能跨语句持有到提交或回滚。

3. `MDLLock`
保护元数据语义，协调 DDL 与 DML，避免表定义在使用中被破坏。

这是生产可用设计的基本纪律。如果三类对象混在一起，系统很快会出现：

- 锁顺序不可控
- 持锁时间失真
- 死锁难以分析
- DDL 与 DML 行为不一致

## 核心数据结构

- `Latch`
  - `Mutex`
  - `RWLock`
  - `SpinLatch` 或混合锁

- `LockManager`
  事务锁管理器，负责授予、等待、唤醒、冲突矩阵和死锁检测。

- `LockRequest`
  包含：
  - `txn_id`
  - `lock_type`
  - `resource_id`
  - `granted`
  - `wait_start_ts`

- `LockResource`
  锁资源对象，可对应表、记录、gap、元数据对象。

- `DeadlockDetector`
  维护 wait-for graph 或等价结构。

- `MDLContext`
  会话级元数据锁上下文，绑定到 `Session / THD`。

## 锁层次与职责边界

### Latch

典型使用场景：

- 保护 buffer pool hash 表
- 保护 B+Tree 页结构修改
- 保护事务管理器中的活动事务表

规则：

- 不跨用户语句长时间持有
- 尽量不跨磁盘 I/O
- 不参与业务可见性语义

### 事务锁

典型使用场景：

- `SELECT ... FOR UPDATE`
- 更新、删除、插入冲突
- 防止幻读的 gap / next-key 保护

规则：

- 和事务生命周期绑定
- 参与死锁检测
- 必须能解释等待原因

### 元数据锁

典型使用场景：

- DML 期间持有表级共享元数据锁
- DDL 期间申请排他元数据锁

规则：

- DML 和 DDL 必须统一走同一套元数据锁框架
- 打开表、关闭表、执行 DDL 的路径都要接入

## 锁兼容矩阵

第一版就应该把兼容矩阵明文化，而不是散落在代码 if/else 里。至少需要这些对象类型：

- 元数据锁：`MDL_SHARED_READ`, `MDL_SHARED_WRITE`, `MDL_EXCLUSIVE`
- 事务锁：`IS`, `IX`, `S`, `X`
- 可选扩展：`GAP`, `NEXT_KEY`, `INSERT_INTENTION`

设计时建议每类锁都有独立兼容矩阵函数，避免把不同层次的锁混在同一张表里。

## 关键流程

### 查询 / DML 路径

1. 打开表前申请元数据锁
2. 进入执行器后按访问路径定位记录
3. 访问页时申请短期 latch
4. 需要事务隔离时向 `LockManager` 申请事务锁
5. 冲突时进入等待队列，触发死锁检测
6. 获得锁后继续执行，事务结束时统一释放

### DDL 路径

1. 申请目标对象的排他元数据锁
2. 阻塞新的 DML 进入
3. 等待旧的共享元数据锁释放
4. 执行元数据变更与物理变更
5. 提交后失效相关缓存并释放锁

## 死锁检测设计

第一版就要做最小死锁检测，否则事务系统在复杂 SQL 下不可用。

推荐方案：

- 每次事务进入等待时，将“等待者 -> 被等待者”加入 wait-for graph
- 做局部环检测，而不是周期性全图扫描
- 发现环时选择一个受害者回滚

受害者选择策略建议第一版简单可解释：

- 优先回滚持锁少、undo 少、运行时间短的事务

不要让“谁先检测到谁倒霉”成为默认策略，这会让线上行为非常难解释。

## 锁顺序设计

数据库最怕的不是“锁很多”，而是没有稳定锁顺序。

建议至少约定以下全局顺序：

1. `MDLLock`
2. 全局事务管理器锁
3. 表级事务锁 / 意向锁
4. 页级 latch
5. 记录级事务锁

是否完全采用这个顺序可以根据实现调整，但必须明确写进设计文档并在核心路径上遵守。

## 热点争用治理

接近生产可用的单机内核，锁设计不能只考虑正确性，还要考虑热点场景：

- 热点页
- 热点主键
- 热点事务管理器结构
- 热点元数据缓存对象

建议第一版预留这些治理手段：

- Lock manager 哈希分片
- buffer pool 分片
- 记录锁资源按对象哈希桶管理
- wait queue 显式化，便于后续观测

## 工程实现建议

- latch 与 lock 不可混用；两者持有时间和语义完全不同。
- 锁顺序必须文档化，不然后期非常难治理死锁。
- 元数据锁不要省略，否则 DDL 一定会在后期变成系统漏洞。
- 每个锁请求都要带会话和 SQL 上下文信息，便于诊断。
- 死锁检测必须和 wait queue 集成，而不是独立旁路实现。

## 第一版应该做什么，不该做什么

### 应该做

- 行锁
- 意向锁
- 元数据锁
- wait-for graph 死锁检测
- 基础 lock wait 诊断信息

### 不该做

- 一开始就实现所有 next-key 细节
- 一开始就做极其复杂的锁升级 / 降级体系
- 一开始就做过度复杂的锁公平性策略

## 最小可用版本

- 记录级排他锁
- 基础共享锁 / 意向锁
- 元数据锁
- 死锁检测与受害者回滚

## 继续演进方向

- 更精细的 gap lock / next-key lock
- lock wait instrumentation
- 热点争用分析
- 锁管理器分片与 NUMA 感知优化
