# 索引结构设计

## 模块目标

索引模块决定查询是否能在生产负载下稳定工作。它不是一个“加速查询的附属功能”，而是单机事务内核的主干结构。它要回答：

- 主键和二级索引如何组织
- 点查、范围查、排序、覆盖索引如何支持
- 插入、更新、删除时索引如何维护
- 页分裂、页合并、purge 和恢复如何与索引结构配合
- 优化器如何稳定地消费索引能力

## 当前仓库参照实现

关键参照：

- `storage/innobase/btr/`: B+Tree 实现
- `storage/innobase/page/`: 页格式与页导航
- `storage/innobase/row/`: 行与索引联动、purge 与索引维护
- `storage/innobase/dict/`: 索引元数据定义
- `sql/opt_range.cc`: SQL 层如何利用索引访问能力
- `sql/handler.h`: 引擎暴露给 SQL 层的索引接口

如果以当前仓库为参照，最重要的不是“B+Tree 能查找”，而是以下协作关系：

- 聚簇索引与记录物理组织耦合
- 二级索引与回表耦合
- purge 与 delete-mark 耦合
- redo / recovery 与页级索引操作耦合

## 如果你自己实现，应该怎么抽象

对于 InnoDB 风格单机引擎，建议采用：

- 聚簇索引：主键索引叶子页直接存行
- 二级索引：叶子页存二级键 + 主键值
- 非叶子页：存 separator key + child page pointer
- 范围扫描：通过叶子页链表或稳定页间导航完成

建议分成四层对象：

1. `IndexDef`
定义索引的逻辑结构，例如是否聚簇、包含哪些列、比较规则和唯一性。

2. `Btree`
索引实例，负责 root page、层高、统计信息和结构操作入口。

3. `BtreeCursor`
负责查找、范围扫描、插入位置定位、页内游标推进。

4. `IndexEntryFormatter`
负责逻辑 key 与页内物理 entry 编码转换。

这样做的好处是：

- 逻辑索引定义和物理 B+Tree 结构解耦
- 扫描和结构修改共用同一套 cursor 语义
- 后续支持前缀索引、复合索引和在线建索引时边界清晰

## 关键不变量

索引结构设计时，必须优先写清楚不变量，而不是 API：

1. B+Tree 任一非根页都满足最小/最大填充约束。
2. 非叶子页中的 separator key 保证子树 key 空间有序。
3. 聚簇索引叶子页是行记录的权威物理组织位置。
4. 二级索引叶子页必须能稳定回表到聚簇索引。
5. 页内 slot 有序，页间叶子链路有序。
6. redo replay 后这些不变量仍然成立。

## 聚簇索引设计

聚簇索引是第一版最应该优先做对的索引类型。

建议采用下面的语义：

- 表的主记录只在聚簇索引叶子页中存一份
- 主键顺序决定记录物理分布
- 全表扫描本质上是聚簇索引叶子页范围扫描

这种设计的好处：

- 主键点查、范围查天然高效
- 回表目标唯一、稳定
- MVCC 的版本指针与行记录可以稳定绑定

代价是：

- 主键更新非常昂贵，等价于 delete + insert
- 插入顺序若高度随机，会带来更频繁页分裂

因此文档中应明确：第一版尽量不强调高效支持主键更新。

## 二级索引设计

二级索引建议采用：

- key 部分：二级索引列
- suffix 部分：主键列

不要在第一版让二级索引直接保存“物理行地址”，因为：

- 页分裂、重组、purge 后物理地址不稳定
- 恢复后重定位成本高
- DDL / compact / reorganize 复杂度暴涨

主键作为回表句柄虽然更大，但语义稳定，和 MySQL 当前体系也一致。

## 复合索引与前缀匹配

第一版就应该把复合索引语义定义清楚，因为优化器和执行器都会依赖它。

建议明确：

- 复合索引按 key part 顺序编码
- 范围查询只支持“左前缀连续匹配”高效利用
- 一旦遇到非等值范围，后续列一般不再参与导航，只能用于过滤或覆盖判断

这部分即便第一版不做极复杂优化，也必须写进设计约束，否则后面优化器接口会反复返工。

## 查找路径设计

### 点查

1. 从 root page 开始
2. 逐层在非叶子页二分或 slot 导航
3. 到达叶子页后定位目标槽位
4. 若是二级索引，则根据主键值回到聚簇索引

### 范围查

1. 根据左边界定位起始叶子页
2. 从起始槽位顺序遍历
3. 到达页尾则沿 `next_leaf` 前进
4. 超出右边界时结束

范围查设计好以后，排序优化和区间访问优化基本都有了落点。

## 插入路径设计

插入建议拆成：

1. 通过 cursor 定位叶子页插入位置
2. 判断目标页剩余空间是否足够
3. 若足够，页内插入并维护 slot 顺序
4. 若不足，执行页分裂
5. 将 separator key 向父页上推
6. 必要时递归分裂直到 root

页分裂一定要区分：

- 乐观插入：无需分裂
- 悲观插入：需要分裂和父页修改

这是第一版就应该区分的关键路径，因为它们的 latch 持有模式和 redo 粒度完全不同。

## 删除与 purge 路径

对于接近生产可用的事务引擎，建议删除分两步：

1. 前台事务执行 delete-mark
2. purge 线程在旧版本不再可见时真正物理删除索引项

这意味着索引层需要支持：

- delete-mark 记录存在但逻辑不可见
- purge 后的物理压缩或 slot 回收

不要在第一版就把 delete 实现成“前台直接物理删掉所有索引项”，这会和 MVCC、回滚、恢复路径强烈冲突。

## 页分裂、页合并与重组

### 页分裂

重点不是“把页一分为二”，而是：

- 选哪个 split point
- separator key 如何选择
- sibling pointer 如何更新
- 父页如何稳定引用新页

### 页合并

第一版可以保守处理：

- 不急于频繁合并
- 优先允许页变稀疏
- 后台或特定维护路径再做页合并

原因很现实：页合并比页分裂更容易把并发、恢复和游标一致性搞复杂。

### 页重组

建议支持页内 compact/reorganize，用于：

- 回收碎片
- 保持 slot 和记录布局紧凑

但第一版不要做太激进的自动重组策略。

## 与优化器的接口边界

索引层至少要向 SQL 层稳定暴露这些能力：

- 是否唯一
- 是否聚簇
- 是否支持范围访问
- 是否支持有序扫描
- 是否覆盖查询需要的列
- 基础基数与页数统计

不要让优化器直接感知底层页结构；SQL 层只需要能力、代价输入和 cursor 语义。

## 与事务、恢复的耦合点

索引设计和事务/恢复不是并列关系，而是强耦合：

- 聚簇索引记录上要挂接 MVCC 所需版本信息
- delete-mark 与 purge 直接影响索引项生死
- 页分裂、页重组和删除都要产生 redo
- 恢复阶段必须能幂等重放索引页修改

因此索引层的 redo record 类型建议第一版就覆盖：

- 插入记录
- delete-mark
- 物理删除
- 页分裂
- 页重组

## 工程实现建议

- 第一版优先把 B+Tree 做正确，不要先上跳表或 LSM 作为主事务引擎主索引。
- 聚簇索引优先，二级索引次之；先保证聚簇索引完整闭环。
- 二级索引一定要考虑回表成本，这是优化器和执行器的关键输入。
- 主键设计要强约束：没有稳定主键时，很多工程问题会急剧恶化。
- 页分裂路径和普通插入路径必须分开建模。
- 删除一定要兼容 MVCC，不要做“前台直接物理删除”的简化实现。

## 第一版应该做什么，不该做什么

### 应该做

- 聚簇索引
- 二级索引
- 复合索引基础语义
- 点查与范围查
- 页分裂
- delete-mark + purge
- 基础索引统计

### 不该做

- 一开始就做复杂 page merge 策略
- 一开始就做自适应哈希索引
- 一开始就做复杂在线索引构建

## 最小可用版本

- 主键点查与范围查
- 二级索引点查与范围查
- 覆盖索引判断
- 插入导致的页分裂
- delete-mark 与 purge 的基础路径

## 继续演进方向

- 自适应哈希索引
- 更复杂的 page split / merge 策略
- 索引统计信息自动刷新
- 在线建索引
- 针对热点页的并发优化
