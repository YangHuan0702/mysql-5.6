# 测试体系与工程化

## 模块目标

数据库内核的可靠性主要靠测试体系和工程纪律保证，而不是靠“代码写得很小心”。这一模块负责定义：

- 单元测试如何覆盖核心模块
- SQL 回归如何验证外部语义
- 如何做崩溃恢复、并发和性能回归

## 当前仓库参照实现

关键参考：

- `unittest/gunit/`
- `tests/`
- `mysql-test/`
- `mysql-test/suite/innodb`, `mysql-test/suite/rocksdb`, `mysql-test/suite/rpl`

当前仓库最大的价值之一，就是它把“引擎级回归”和“SQL 级回归”长期并存维护。

## 如果你自己实现，应该怎么抽象

建议至少建立三层测试：

- 模块单元测试
- 引擎组件测试
- SQL 回归测试

外加两类专项测试：

- 崩溃恢复测试
- 并发压力与死锁测试

## 核心数据结构

- `TestHarness`
- `CrashScenario`
- `SQLGoldenCase`
- `WorkloadProfile`

## 关键流程

1. 单元测试验证数据结构、锁、日志和解析逻辑
2. 组件测试验证 B+Tree、事务、恢复链路
3. SQL 回归验证语义与兼容行为
4. 故障注入验证崩溃后一致性
5. 压测验证性能回归和争用退化

## 工程实现建议

- 第一版就建立 SQL golden tests，后面每次修复 bug 都补回归。
- WAL、恢复、锁和 DDL 都必须有故障注入测试。
- 不要只测成功路径；数据库最致命的问题大多在失败路径。

## 最小可用版本

- 单元测试框架
- 基础 SQL 回归框架
- 崩溃恢复专项测试
- 并发死锁测试

## 继续演进方向

- 随机 SQL 生成与 fuzz
- 长时稳定性测试
- 多版本兼容回归
- 自动化性能基线
