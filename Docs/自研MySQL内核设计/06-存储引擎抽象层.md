# 存储引擎抽象层

## 模块目标

该模块定义 SQL 层如何调用底层存储引擎，并隔离“通用 SQL 语义”和“具体存储实现细节”。它决定了：

- SQL 层访问数据的最小接口集
- 多存储引擎是否可插拔
- 事务、锁、扫描、索引访问如何向下传递
- DDL、恢复、统计信息、能力协商如何向上暴露

这一层如果设计得太薄，SQL 层会被存储实现反向污染；设计得太厚，又会变成一个低效、模糊的万能接口层。

## 当前仓库参照实现

关键参考：

- `sql/handler.h`, `sql/handler.cc`
- `include/mysql/plugin.h`
- `storage/innobase/`
- `storage/myisam/`
- `storage/rocksdb/`

当前仓库里的 `handler` / `handlerton` 就是典型参照。SQL 层不直接理解 InnoDB 页结构，而是通过统一接口完成：

- scan
- index read
- write row
- update row
- delete row
- commit / rollback
- 能力位查询

同时 `plugin.h` 说明：存储引擎在 MySQL 里本质上是插件，只是 SQL 层围绕它们提供了一套很重的协调框架。

## 如果你自己实现，应该怎么抽象

如果目标是接近生产可用的单机 MySQL，建议保留“引擎抽象层”，但第一版只实现一个主引擎。这样既保留架构边界，又避免一开始就陷入多引擎兼容复杂度。

建议抽象三层接口，而不是只有两层：

1. `StorageEngine`
负责数据库级能力：

- 打开表
- 创建/删除表
- 启动恢复
- 提供事务对象
- 暴露能力矩阵

2. `TableHandle`
负责表级访问：

- 表扫描
- 索引定位
- 插入、更新、删除
- 统计信息读取

3. `EngineTxn`
负责引擎事务上下文：

- 当前事务读写集合
- undo/redo 关联
- 锁集合
- commit / rollback hooks

这样拆分之后，SQL 层就能清楚地分别依赖：

- 全局引擎能力
- 表访问能力
- 事务能力

## 核心数据结构

- `StorageEngine`
  - `engine_name`
  - `capabilities`
  - `open_table()`
  - `create_table()`
  - `drop_table()`
  - `begin_txn()`
  - `recover()`

- `TableHandle`
  - `table_def`
  - `engine_ref`
  - `scan_cursor`
  - `index_cursor`
  - `read_row()`
  - `write_row()`
  - `update_row()`
  - `delete_row()`

- `IndexCursor`
  负责索引扫描与范围推进。

- `EngineTxn`
  - `engine_txn_id`
  - `state`
  - `undo_ctx`
  - `redo_ctx`
  - `held_locks`

- `EngineCapabilities`
  至少包含：
  - `supports_transactions`
  - `supports_mvcc`
  - `supports_covering_index`
  - `supports_range_scan`
  - `supports_online_ddl`
  - `supports_ordered_scan`

## 为什么第一版仍然要保留抽象层

很多自研数据库在早期都会犯一个错误：

> 反正第一版只做一个事务引擎，SQL 层直接调用这个引擎内部对象就行。

这会带来几个长期问题：

- 优化器会直接依赖存储页布局
- 执行器会直接依赖内部游标对象
- DDL、统计信息、恢复和事务边界变得非常难替换
- 后面想引入 memtable / analytical engine / mock engine 做测试时几乎推倒重来

因此即使第一版只有一个主引擎，也必须把接口边界立起来。

## 能力矩阵设计

SQL 层不能假设所有引擎都支持相同行为，因此抽象层要显式暴露能力矩阵。

建议至少覆盖：

- 是否支持事务
- 是否支持 MVCC
- 是否支持唯一索引
- 是否支持覆盖索引扫描
- 是否支持顺序索引扫描
- 是否支持范围扫描
- 是否支持外部排序优化
- 是否支持在线 DDL

能力矩阵的用途不只是“多引擎兼容”，即使只有一个主引擎，也能帮助优化器、DDLExecutor 和测试框架稳定地消费引擎特性。

## 与 SQL 层的边界

建议明确：

- SQL 层负责语义
- 存储引擎负责物理实现

例如：

- “这是一条 `UPDATE` 语句，需要当前读并加锁”属于 SQL 层语义
- “如何定位记录、生成 undo/redo、修改页、申请记录锁”属于引擎层实现

不要让 SQL 层直接操纵页、undo、redo 或记录锁对象。SQL 层最多通过统一事务与访问接口表达需求。

## 打开表与句柄生命周期

建议把“打开表”分成两步：

1. SQL 层根据元数据获取 `TableDef`
2. 通过引擎创建 `TableHandle`

`TableHandle` 生命周期建议和语句或执行上下文绑定，而不是和全局缓存永久绑定。原因是：

- 句柄内部可能携带事务状态或 cursor 状态
- DDL 后旧句柄需要平滑淘汰

## 事务协调设计

`EngineTxn` 不应被藏在 `TableHandle` 里。推荐的调用模型是：

1. `Session` 开始事务
2. SQL 层向主引擎获取 `EngineTxn`
3. 所有 `TableHandle` 操作都显式接收该 `EngineTxn`
4. commit / rollback 时由 SQL 层触发引擎事务提交

如果第一版就把事务状态藏在表句柄里，后面一旦出现同事务多表访问、DDL 混入、只读视图或 savepoint，就会全面崩坏。

## DDL 与引擎抽象层

抽象层必须考虑 DDL，不然它就只够支撑 DML。

建议至少保留这些接口：

- `create_table(def)`
- `drop_table(def)`
- `build_index(def, index_def)`
- `alter_table(old_def, new_def, alter_plan)`

这样 DDLExecutor 就能只负责：

- 校验
- 元数据变更编排
- MDL
- 恢复协调

具体文件、页、索引构建细节留给引擎层。

## 统计信息接口

优化器依赖统计信息，但不能直接读取页结构。

建议提供：

- `estimate_row_count(table)`
- `estimate_index_cardinality(index)`
- `estimate_range_rows(index, range)`
- `collect_runtime_stats()`

这些接口第一版实现可以简单，但边界必须先定好。

## 错误语义与返回值设计

抽象层最容易被低估的一点是错误语义。

建议至少区分：

- 逻辑不存在：例如 key not found
- 可重试冲突：例如死锁、锁等待超时
- 约束失败：例如唯一键冲突
- 内部故障：页损坏、结构异常、恢复失败

不要在第一版把所有错误都折叠成 `bool success / fail`，这会让 SQL 层难以正确处理异常路径。

## 与恢复、备份、可观测性的边界

引擎抽象层不只服务前台执行，还要预留以下边界：

- 恢复时的 `recover()`
- checkpoint / flush 观测
- 表与索引级统计信息
- 备份接口或 snapshot hook

即使第一版不实现完整备份，也应该把这些能力作为抽象层的可扩展点保留出来。

## 工程实现建议

- 第一版就区分“事务对象”和“表访问对象”，不要把事务状态藏在表句柄里。
- 能力矩阵必须显式化，例如是否支持事务、是否支持覆盖索引、是否支持范围扫描、是否支持在线 DDL。
- 抽象层不要设计成“什么都能做”的万能接口；接口越肥，后续越难优化。
- SQL 层不要直接拿到页、记录锁、undo/redo 细节对象。
- 统计信息接口和 DDL 接口第一版就应该预留。

## 第一版应该做什么，不该做什么

### 应该做

- `StorageEngine` / `TableHandle` / `EngineTxn` 三层接口
- 单主引擎实现
- 访问、事务、DDL、统计信息的基本接口
- 明确错误语义
- 显式能力矩阵

### 不该做

- 一开始就做完整多引擎兼容
- 一开始就暴露极多细碎物理接口
- 一开始就把 SQL 层和引擎内部对象打通

## 最小可用版本

- 打开表
- 主键和二级索引扫描
- 行级增删改查
- 事务提交与回滚
- 基础统计信息
- 建表与删表接口

## 继续演进方向

- 多引擎真正并存
- 更复杂的引擎能力协商
- DDL capability matrix
- 面向复制和备份的引擎 hooks
- 更细粒度观测和错误诊断能力
