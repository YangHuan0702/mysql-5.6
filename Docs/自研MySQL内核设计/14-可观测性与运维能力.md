# 可观测性与运维能力

## 模块目标

生产可用内核不仅要“能跑”，还要“能看见、能定位、能运维”。该模块覆盖：

- 错误日志
- 状态变量
- 语句级诊断
- 性能观测

## 当前仓库参照实现

关键参考：

## 如果你自己实现，应该怎么抽象

建议至少建立三层观测面：

- `ErrorLog`
- `StatusCounters`
- `PerformanceInstrumentation`

如果第一版没有 performance schema 级别复杂度，也至少要有结构化状态计数器和错误日志。

## 核心数据结构

- `LogEvent`
- `StatusVar`
- `StatementStats`
- `WaitEvent`
- `MetricsRegistry`

## 关键流程

1. 请求进入时创建语句级统计上下文
2. 执行过程中累计扫描行数、返回行数、锁等待等信息
3. 错误和警告统一写日志与会话诊断区
4. 管理命令读取全局与会话状态

## 工程实现建议

- 先做“低开销、可长期打开”的基础指标，再做重型 profiling。
- 每个核心模块都要预留 instrumentation hook，但不要把统计逻辑硬编码在主流程里。
- 错误日志必须包含模块、会话、对象和错误码信息。

## 最小可用版本

- 错误日志
- 基础状态变量
- 会话级 warning / error 诊断
- 语句级执行统计

## 继续演进方向

- Performance Schema 风格系统表
- 细粒度等待事件
- 更完整的 tracing
- 在线性能诊断工具
