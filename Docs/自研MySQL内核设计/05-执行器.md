# 执行器

## 模块目标

执行器负责消费优化器输出的物理计划，并驱动表达式求值、临时表、排序、聚合和存储引擎访问。它是 SQL 层与存储层之间最频繁的运行时桥梁。

## 当前仓库参照实现

关键参考：

- `sql/sql_executor.cc`: `JOIN::exec()`
- `sql/sql_select.cc`: 执行前准备和部分执行逻辑
- `sql/filesort.cc`, `sql/sql_tmp_table.cc`: 排序与临时表
- `sql/item*.cc`: 表达式求值
- `sql/handler.cc`: 落到引擎访问接口

## 如果你自己实现，应该怎么抽象

建议用迭代器风格执行模型：

- `open()`: 初始化算子
- `next()`: 拉取下一行
- `close()`: 释放资源

典型执行节点：

- `TableScanNode`
- `IndexScanNode`
- `FilterNode`
- `ProjectNode`
- `NestedLoopJoinNode`
- `SortNode`
- `AggregateNode`
- `MaterializeNode`

这种设计和 MySQL 现有执行风格不完全等同，但更适合自研时维持边界清晰。

## 核心数据结构

- `ExecContext`
- `ExecNode`
- `RowBatch` 或 `RowView`
- `ExpressionEvaluator`
- `TempTable`
- `SortBuffer`

## 关键流程

1. 根据物理计划构造执行节点树
2. `open()` 全部节点
3. 从根节点不断 `next()` 取结果
4. 节点内部驱动表达式求值与子节点访问
5. 必要时使用临时表、排序缓冲和聚合状态
6. 执行结束后 `close()` 释放资源

## 工程实现建议

- 第一版优先做 row-at-a-time iterator，先保证正确性，再考虑 vectorized execution。
- 执行器必须和事务上下文强绑定，否则锁、快照、可见性和错误恢复会断裂。
- 临时表要显式区分内存临时表和落盘临时表。
- 表达式求值不要直接耦合 AST，使用规范化后的执行期表达式对象。

## 最小可用版本

- 表扫描、索引扫描
- 过滤、投影
- 嵌套循环连接
- 排序
- 基础聚合
- 临时表

## 继续演进方向

- 向量化执行
- 更高效的 hash aggregation / hash join
- 更细粒度执行统计
- 自适应内存控制与执行级 spilling
